# Golos Meet — план развития

Обновлено: 30 октября 2026.

## Как ведём работу

Процесс — в `AGENTS.md`. Каждый этап ведётся в отдельном чате и worktree; критерии и актуальное состояние находятся в GitHub issues:

1. Общая основа и настройка workflow — https://github.com/marcusaure1ius/golos-meet/issues/2
2. API Толка и индикация — https://github.com/marcusaure1ius/golos-meet/issues/3
3. Проекты, импорт и локальный поиск — https://github.com/marcusaure1ius/golos-meet/issues/4
4. Вопросы и память — https://github.com/marcusaure1ius/golos-meet/issues/5
5. Constance (отложен, не запускается) — https://github.com/marcusaure1ius/golos-meet/issues/6

Активный объём — этапы 1–4: реализация, проверки, независимое ревью и тестовая интеграция для общей ручной проверки пользователем. Координацию и разрешение запуска по зависимостям ведёт чат «Координация · Golos Meet». Этап 5 отложен.

Любую существенную неясность обязательно уточняем у пользователя до зависимых действий: неоднозначные требования, способ отправки данных, права и серверную конфигурацию не выбираем молча. Понятную независимую работу продолжаем; повторного подтверждения уже ясно разрешённых действий не требуется.

Этапы 2 и 3 зависят от принятой общей основы, но не друг от друга. Этап 4 зависит от 3, этап 5 — от 4 и пока отложен. Зависимость закрывается по независимо проверенному коду, принятому в `codex/product-preview`; ждать слияния в `main` не нужно. Координатор проверяет PR, проверенный SHA и наличие результата в preview, затем обновляет согласованные статусы issues. Подготовительные чаты до разрешения запуска только читают контекст. Agent Board не используется.

Рабочие ветки этапов начинаются от актуального `origin/codex/product-preview` после fetch, их PR направляются в `codex/product-preview`. Каждый PR проходит независимое ревью конкретного head SHA. Координатор по разрешению пользователя может объединять в preview только проверенные изменения, сверяя текущий head с результатом ревью; новый SHA требует повторной проверки затронутых путей. Сам ревьюер PR не сливает.

Общая основа [PR #7](https://github.com/marcusaure1ius/golos-meet/pull/7), проверенный head `f1107dd4ab0feac115358348edeb9e14b77c70d7`, принята в preview merge-коммитом `2d2826a2bb88e98a5eb6d7d965964d0d0bfad828`. Это позволяет продолжить зависимые этапы по разрешению координатора.

`main` остаётся неизменным до общей ручной проверки всего согласованного продукта пользователем. Итоговый [PR #8](https://github.com/marcusaure1ius/golos-meet/pull/8) (`codex/product-preview` → `main`) остаётся draft и ждёт отдельного явного разрешения пользователя после этой проверки; auto-merge не включать. Принятие отдельных этапов в preview не означает готовности продукта к этому слиянию.

## Согласованные границы

- Проект объединяет встречи, документы, решения, открытые вопросы и связанные задачи.
- Интеграция с календарём не нужна. Проект определяется по содержимому, правилам и исправлениям пользователя.
- Извлечение текста, OCR, разбиение на фрагменты, эмбеддинги и поиск выполняются на Mac.
- Генерация на этапе разработки — OpenRouter за заменяемым интерфейсом.
- Отправка фрагментов документов и производной памяти разрешается отдельно для каждого проекта; по умолчанию запрещена.
- Constance остаётся источником истины для статусов связанных задач.
- Исходные записи и документы сохраняются. Обзор проекта можно пересобрать из источников.

## Что установлено при обследовании

- В клиенте Толка настроен `https://alfabank.ktalk.ru` — адрес облачного пространства. `/api/Users/profile` доступен по HTTPS и возвращает 401 без ключа. Доступ с ключом и права этой организации ещё не проверены.
- В Keychain сервиса `golos-meet` найдена запись `openrouter-api-key`. Ключ Толка в этом сервисе не найден. Значения секретов не выводились.
- Исторически запись управлялась Core Audio и окнами. В #41 добавлено явное API-only управление; подключение/комнаты/identity уже приняты, живая организация и звонок ещё не проверены.
- В актуальной спецификации PAT есть `/api/Users/profile`, `/api/Calendar` и `/api/Rooms/{roomName}/online-users`. Calendar в продукт не подключаем.
- Public API описывает `UserConnectedToRoom`, `UserDisconnectedFromRoom`, `ConferencesStarted`, `ConferencesFinished`. Вебхуки требуют сервера, ключа пространства и соответствующих прав; PAT и ключ пространства — разные способы подключения.
- На данном Mac (Apple Silicon, 24 ГБ RAM) `NLEmbedding.sentenceEmbedding(for: .russian)` возвращает nil. Английская модель доступна; использовать её для русского поиска как незаметную замену нельзя.
- Проверен локальный кандидат `intfloat/multilingual-e5-small`, 384 измерения, ONNX Runtime CPU (4 потока). Повторный полностью офлайн-прогон: загрузка с диска 0,47 с, медиана короткого вопроса 2,38 мс, пиковая память процесса 1,41 ГиБ, попадания top-1 7/8 и top-5 8/8. Веса с токенизатором занимают 487 МБ. Это проверка технической возможности на 10 коротких фрагментах, не оценка качества рабочего архива. Для приложения ещё нужны бандлинг runtime, управление загрузкой весов, токенизация и проверка на реальных проектах. Воспроизводимый эксперимент и JSON-результат находятся в `research/`.

## Этап 1. Техническая основа и проверяемые контракты

- [x] Клиент API Толка: HTTPS, токен только в заголовке, запрет передачи токена при редиректе, понятные ошибки 401/403/429, тесты транспорта.
- [x] Локальное извлечение TXT/Markdown, DOCX, PDF и PNG/JPEG. OCR для сканов. Сохранение страниц/номеров фрагментов; ошибки пустого/зашифрованного/неподдерживаемого файла.
- [x] Модель проекта и политика облачной генерации, отдельные от UI и конкретного провайдера.
- [x] Разбиение текста с перекрытием и устойчивыми ссылками на источник. Семантические векторы содержат идентификатор модели; смешивать векторы разных моделей нельзя.
- [x] Тесты на локальных синтетических файлах; никакие пользовательские документы автоматически не отправляются в сеть.

Дополнительно реализован `KnowledgeAnswerGenerator` поверх существующего `ChatCompleter`: запрос получает только выбранные фрагменты, проверяет политики всех проектов-владельцев источника до транспорта и отклоняет неизвестные ссылки в ответе. В тестах сетевой транспорт заменён, живые документы в OpenRouter не отправлялись.

Результат: проверенный фундамент для импорта и поиска. Новые модули пока не подключены к пользовательскому интерфейсу; автоматическая запись продолжает работать существующим способом до завершения этапа 2. Семантическая модель выполнена в отдельном исследовательском процессе, не встроена в приложение.

## Этап 2. Запись через API Толка и индикация

- Ввести адрес пространства и отдельный API-ключ в настройках; хранить ключ в Keychain.
- Использовать PAT и явно заданные комнаты; пользователь выбрал поиск себя по email и явное подтверждение userKey. Живой ключ/права проверяются отдельно, вебхуки и сервер-приёмник не входят.
- Пользователь звонит только с этого Mac и всегда входит muted. В явно включённом API-режиме свежий present выбранного аккаунта запускает запись без IsRunningInput/окон/кнопки каждого звонка, достоверный absent завершает. Один Mac — допущение пользователя, API не доказывает устройство. Native process/capture readiness проверяется отдельно.
- Обработать дубли, переподключение, потерю сети, перезапуск Mac и истечение ключа; явно описать ограничение участия с других устройств. Состояние «API недоступен» не выдавать за «встречи нет».
- Ограничить системный захват процессами Толка. Подтверждать старт после готовности обеих дорожек.
- В строке меню показывать длительность и состояние захвата. Тишина/mute не считаются ошибкой. При выходе сохранить запись, короткую ручную запись не удалять.

Критерий: синтетическая интеграция проходит production coordinator/Recorder; живые PAT/вход/выход/muted join/mute/переподключение/сон/дорожки/TCC проверяются на отдельно выбранном звонке. Нет условия имени окна/активности mic. Отдельная проверка телефона не выдаётся за реализованную идентификацию устройства; пользователь выбрал один Mac.

## Этап 3. Проекты, импорт и локальный поиск

- Добавить дерево проектов и «Входящие», ручное назначение существующих встреч без переноса аудиофайлов.
- Локальная SQLite-база: проекты, связи источников, версии, фрагменты, состояние индексации, эмбеддинги. Оригиналы хранятся файлами.
- Импорт документов с прогрессом, отменой, дедупликацией по содержимому и повторной индексацией изменённых файлов.
- Отдельная очередь индексации не блокирует запись и ASR.
- Запустить мультиязычную модель локально. Для E5 соблюдать `query:`/`passage:`, нормализацию, лимит контекста и версию модели.
- Сравнить модели на русских вопросах и фрагментах: recall@5, холодный старт, время запроса, скорость индексации, пиковая память, размер на диске.
- Объединить полнотекстовый и векторный поиск. Результат ведёт к странице документа или таймкоду встречи.
- Автораспределение: локальные правила и сходство с доверенным контекстом проекта; буквальное имя — дополнительный признак. Семантическое назначение подтверждается предметными терминами и сравнением конкурентов; при отрицании/неоднозначности — предложение. Ручные исправления сохраняются, auto/proposal не обучают контекст. Новые проекты сначала предлагать.

Критерий: два-три реальных проекта, существующие встречи и документы доступны через локальный поиск; содержимое не отправляется наружу.

## Этап 4. Вопросы и память проекта

- Отбор контекста локально. До сетевого запроса проверять разрешение проекта, включая производные конспекты и источники, связанные с несколькими проектами.
- Генератор ответа зависит от `ChatCompleter`, в разработке используется OpenRouter. Индекс не зависит от поставщика генерации.
- Ответы с источниками, признание недостатка данных, различение даты источника и даты решения. Текст источников — данные, а не команды модели.
- Версионируемая память: решения, договорённости, изменения сроков, вопросы, заявления о выполнении. Конфликты сохраняются со ссылками, ручные исправления не затираются.
- Панель контекста проекта доступна во время встречи. Потоковая ASR и автоматические подсказки по живому разговору — отдельный следующий этап.

Критерий: после новой встречи обзор обновляется, каждый вывод проверяется по источнику, история не теряется.

## Этап 5. Constance — отложен

- Явно сопоставить проект с environment и при необходимости epic/category.
- Создать связанную задачу по выбранной договорённости; хранить external task id и устойчивую связь с источником.
- Дедупликация при повторной обработке/повторной отправке. Статусы задач поступают из Constance.
