# Golos Meet — рабочий процесс

## Начало работы

Прочитай этот файл, `CLAUDE.md`, нужный раздел `DEVELOPMENT_PLAN.md` и GitHub issue.
Перед изменениями проверь `git status`, текущую ветку и зависимости issue.
Инженерные детали — в `CLAUDE.md`; этот документ задаёт процесс.

## Ограничения рабочего процесса

- По прямому указанию пользователя Agent Board (также названный «Agent Port») в этом проекте не используется.
- Не подключать и не вызывать навык `agent-board` и MCP `projects-control-work` для работы над Golos Meet.
- Не регистрировать проект, задачи и документы Golos Meet во внутренней доске агентов и не создавать её локальные зеркала.
- Это ограничение относится к Golos Meet; глобальные навыки и другие проекты не менять.

## Контекст

- Техническое устройство и команды проверки описаны в `CLAUDE.md`.
- Согласованный план развития — `DEVELOPMENT_PLAN.md`.
- Пользовательские требования и исправления в текущем чате имеют приоритет над этими документами.

## Задачи и отдельные чаты

- Единственный трекер задач — https://github.com/marcusaure1ius/golos-meet/issues.
- `DEVELOPMENT_PLAN.md` описывает направление и архитектурные решения. Актуальные статусы, зависимости и критерии готовности — в issues; отдельную локальную доску не создавать.
- У каждого из пяти этапов свой чат. Этот координационный чат отвечает за приоритеты, общие решения и согласование границ.
- Чат этапа работает только над своим issue или согласованной подзадачей. Побочные доработки оформляются отдельно.
- Подготовительный чат читает контекст и ждёт команды пользователя «Начинай». Он не меняет файлы, не запускает модель, не отправляет документы в облако и не разворачивает серверы автоматически.
- Перед началом реализации ещё раз прочитай issue и проверь закрытие зависимостей. После общей основы этапы записи Толка и базы знаний могут выполняться независимо. Память зависит от базы знаний, Constance — от памяти.
- Этап 3 достаточно велик для нескольких небольших issue/PR внутри одного чата. Не объединяй SQLite, UI, импорт и runtime эмбеддингов в один непроверяемый diff.
- Для постановки задач используй `.agents/skills/golos-task/SKILL.md`.

## Worktree и ветки

- Один активный issue/PR — отдельная ветка `codex/<issue>-<slug>` и отдельный управляемый worktree Codex.
- Не редактируй основной checkout из чата этапа и не переключай ветку чужого worktree. Не откатывай чужие изменения.
- Новые рабочие ветки начинай от актуального `main`. Подготовительные worktree, созданные до слияния общей основы, должны после её merge обновиться от `origin/main` перед изменениями.
- Уже начатое ядро и правила workflow собраны в исходной ветке `codex/2-workflow-foundation`; это исключение для подготовки общей основы, а не разрешение строить цепочку всех этапов поверх несогласованных PR.
- Каждый worktree использует собственный DerivedData (`make check`); модели, секреты и записи не копируются в git и не скачиваются при подготовке чата.
- Наличие папки `docs/` в основном checkout не означает её наличие в worktree: она игнорируется git. Всё необходимое для реализации и ревью должно быть в issue или версионируемом документе.

## Реализация → проверки → PR

1. Уточни границы issue и обнови его описание при изменении договорённостей. Если инструкция пользователя уже разрешает заведение задач, не требуй повторного подтверждения.
2. В своём worktree реализуй один проверяемый результат. Изменения в обработке данных и записей проверяй на синтетических/временных данных.
3. Выполни `make check`. При изменении Rust дополнительно `make check-rust`. Для UI проверь реальный экран и состояния загрузки/ошибки/пустых данных; используй текущую дизайн-систему приложения.
4. Коммит: `[type] #<issue> краткое описание`, без Co-Authored-By и других трейлеров. В `main` напрямую не коммитить.
5. Отправь ветку и открой PR в `main`. В описании — результат, команды и исход проверок, ограничения, `Closes #<issue>` только для полностью закрываемой задачи; для частичной работы — `Refs #<issue>`.
6. При создании PR прикрепи его к соответствующему чату через инструмент приложения, если он доступен.

`make check` собирает приложение и прогоняет Swift-тесты, исключая реальный ASR E2E. Тестовый host отключает рабочий UI, восстановление, детектор и автоматическую обработку; пути по умолчанию ведут во временное хранилище, а Keychain использует тестовый service. Настоящий ASR E2E требует явно заданных путей к sidecar, модели и выбранному аудио. Настоящие модели, пользовательское аудио, облачные вызовы и операции с реальными задачами проверяются отдельно, когда это нужно по issue. В отчёте не выдавай мок за живую интеграцию.

## Независимое ревью и завершение

- Ревью выполняет отдельный чат/агент, который не реализовывал рассматриваемое изменение. Самопроверка автора полезна, но не заменяет независимое ревью.
- Ревьюер читает `.agents/skills/golos-review/SKILL.md`, критерии issue, описание PR и фактический diff. Проверяет конкретный SHA и сообщает его вместе с результатом.
- Ревьюер работает без редактирования ветки автора, не коммитит исправления и не сливает PR. Замечания возвращаются в чат реализации.
- Автор исправляет подтверждённые замечания и запускает относящиеся к ним проверки. После изменения SHA нужно перепроверить затронутые пути.
- Слияние выполняет пользователь. Не включать auto-merge и не сливать PR без отдельного поручения.
- В конце работы дай короткую передачу контекста: PR и SHA, выполненные критерии, проверки, известные ограничения и следующий шаг. Worktree с неслитой работой не удалять.

## Продуктовые и технические границы

- Интеграция с календарём исключена пользователем.
- Извлечение, OCR, эмбеддинги и поиск — локально. Генерация в разработке — OpenRouter через заменяемый интерфейс.
- Облачная обработка документов и производной памяти разрешается для каждого проекта отдельно; учитываются все владельцы общего источника.
- Секреты — в Keychain, не в репозитории, issue, промптах новых чатов или логах. Не копировать пользовательские записи в worktree.
- Пользовательское имя — Golos Meet; target `golos-meet`, Swift-модуль `golos_meet` и bundle id `com.golos.golos-meet` сохраняются.
- Документация, задачи и общение — по-русски; код и идентификаторы — по-английски.
