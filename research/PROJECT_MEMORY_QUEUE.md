## Хранение и покрытие

Схема v8 добавляет `memory_queue_runtime`, `memory_queue_work`, неизменяемые `memory_queue_batches` и индекс. Старые таблицы v7 и их данные не переписываются. Один work соответствует паре проект × источник. Work содержит стабильный вход, отдельный cycle обработки, generation/attempt для CAS, cursor/total, состояние, зависимости и ключ последнего выбранного запроса. Batch содержит offset/count, действительный v2 selected-input key, disposition completed/unchanged/insufficient и IDs событий.

Worker последовательно выбирает готовые источники round-robin. Один запрос содержит префикс до 12 фрагментов, до 14 тыс. символов сырого текста; префикс дополнительно уменьшается под фактические JSON-лимиты сервиса (24 тыс. символов/64 тыс. UTF-8 байт, 16 тыс. текста с повторёнными заголовками). Только реально выбранный префикс продвигает cursor. Service отклоняет подмену/пропуск фрагментов относительно cursor. Обычный источник из 25 фрагментов проходит 12/12/1; quote-heavy JSON адаптивно разбивается без пропуска.

События журнала, batch disposition и cursor фиксируются одной SQLite-транзакцией. Exact replay принятого service-запроса фиксирует unchanged без сети. Insufficient также фиксируется без выдуманного события; после restart этот batch не отправляется заново. Полное посещение всех фрагментов с хотя бы одним insufficient имеет состояние `insufficient`, а не уверенный завершённый обзор. `partial`, `limited`, `failed`, `stale`, `needsConsent` и отмена не считаются полным покрытием. Повторный event или restart не переотправляет завершённые части неизменного cycle.

## Актуальность и разрешения

Вход очереди учитывает ревизию и epoch источника, поколение/состояние локального задания, индексную модель/размерность/epoch, реальную файловую identity, всех текущих владельцев и политики, модель генератора, контракт принятого extractor v2 и ручную версию выбранного проекта. Зависимости предыдущих batch сохраняют consumed source epochs/revisions/file identities/job generations, всех raw/derived владельцев с политиками и ручные версии затронутых проектов. Смена этих значений создаёт новый cycle и сбрасывает coverage; старые dispositions остаются историей. Отдельный cycle предотвращает коллизию offset даже при прежнем базовом hash после изменения предка.

Сервис сохраняет принятые полные provenance/CAS, actual v2 identity сообщений/schema/model/version/ordered S–M bindings, all-owner проверки перед каждой транспортной попыткой, после ответа и внутри транзакции публикации. Очередь добавляет durable run/generation/attempt/cursor fence и проверки источников предыдущих batch. ABA source/model/owners/policy и late old run не получают права публикации. Producer key не строится из UUID запроса или времени.

Автоматические события журнала сами по себе не ставят готовый источник заново: queue input зависит от ручных изменений, а не от каждого model head. Worker выбирает до восьми пригодных текущих heads с общим бюджетом около 4 тыс. символов и исключает heads, уже потребившие этот же источник. Это ограничивает обратную связь между частями длинного источника. Изменение источника/владельцев/политики/использованного предка или ручной версии инвалидирует зависимую работу.

`localOnly` любого raw/derived владельца блокирует транспорт. `askEveryTime` оставляет работу в `needsConsent`; preview готовится локально только по явному запросу будущей панели. Разрешение относится к одному точному batch, хранится только в памяти и потребляется сервисом однократно. Следующая часть и restart требуют нового preview/согласия. Прежнее согласие не становится фоновым допуском. UI панели в этом PR ещё нет, поэтому новые askEveryTime jobs ожидают её подключения.

## Lifecycle и ограничение ресурсов

Production singleton запускается после существующих indexing/assignment runtime, получает metadata events и реальные index updates, объединяет события с debounce 100 мс и делает резервную проверку каждые 30 секунд. Он использует существующий `QuestionOpenRouterClient`, учитывает `llmEnabled`/модель. Применение настроек отменяет прежнюю задачу и перепроверяет последнее состояние после await: старое включение не может победить новое выключение/stop. Test-host guard расположен до production store/settings/runtime/Keychain. Запись, захват и ASR не вызываются и не ждут очередь; остановка при выходе не задерживает финализацию записи.

В production worker одновременно выполняется одна физическая операция. Deadline 30 секунд немедленно инвалидирует durable lease и отменяет service/task; worker затем дожидается завершения адаптера перед следующей попыткой. Некорректный адаптер, игнорирующий cancellation, может задержать продолжение до собственного возврата. Это видно как failed; не создаётся растущий набор брошенных transport tasks. Перезапуск приложения восстанавливает running в queued/partial, новый durable run запрещает публикацию от старого worker. Тест замены worker с удержанным fake-адаптером специально проверяет durable fence, а не обещает принудительно завершить чужую сетевую операцию.

Горячее окно — до 128 queued/partial/running jobs; claim отложенного задания может временно дать ещё одну running. Остальные пары сохранены как `backpressured` и доступны планировщику round-robin. Snapshot для панели ограничен 256 строками и имеет явный backpressured flag; SQL-планировщик не зависит от этого UI-среза. Один drain обрабатывает до 256 batch, затем отдаёт управление и продолжает новой задачей. Consumed dependencies ограничены 128 источниками, 128 проектами и 128 тыс. символов опорных фрагментов; лимит кандидатов журнала остаётся 256 с принятой возможностью явного ручного освобождения.

Это ограничения активной обработки, а не общий предел архива: сверка metadata обходит существующий каталог, work хранится по всем обнаруженным парам, неизменяемая история batch естественно растёт. Масштаб/производительность реального архива отдельно не измерены. Слишком большой одиночный фрагмент/цепочка получают limited с причиной. Terminal error/limited/stale не запускаются бесконечно от повторных событий. Явный retry ошибок/отмены продолжает с cursor; completed/insufficient остаются no-op до изменения входа/контекста. Отмена остаётся пользовательским решением и при смене входа требует явного retry.

## Миграция и доказательства

`research/memory-queue-37/generate_v7.py` собирает генератор из **замороженных исходников принятого b118fcc**, а не понижает номер новой схемы. Fixture v7 содержит M:N, две версии документа, оригиналы, manual Inbox, pending assignment, FTS/shadow tables, synthetic 2D binary vectors, original+manual memory events/links/head versions/batches/state. Manifest содержит hash исходников, seed и каждого файла.

Тест копирует fixture во временный каталог и сравнивает значения **каждой старой таблицы**, включая BLOB/FTS shadows, старые schema objects и байты оригиналов до/после v8 и restart; выполняет реальный FTS-запрос, foreign_key_check и проверку manual Inbox/pending assignment. Второй тест создаёт конфликтующий объект перед миграцией: ошибка после части DDL откатывает version/schema/все старые значения, затем после удаления sentinel миграция проходит. Принятый PR53 ROLLBACK release fixture, busy_timeout и синхронизация race-тестов не изменены; обновлены только ожидания текущего номера схемы.

Итоговый `make check`: **425 тестов / 596 запусков / 0 ошибок / 0 пропусков / 0 runtime warnings**. Targeted queue+migration: **24 теста / 32 запуска / 0 ошибок / 0 пропусков / 0 runtime warnings**. Build-only native host собран.

Результаты команд и raw migration traces находятся в `memory-queue-37/checks.json` и `memory-queue-37/migration-traces/`. Первые локальные итерации включали ошибочную классификацию invalid draft как stale и две ошибки компиляции вновь добавленных тестов; они исправлены. Итоговые full/targeted результаты относятся к исправленному коду. Ранее принятые артефакты #51/PR52 сохранены без изменения.

Все queue/cloud checks используют настоящие временные ProjectStore/SQLite/import/index/history/service/worker с synthetic текстом, synthetic storage vectors и transport spy. Fake retry — проверка per-attempt gate, а не живой HTTP 503. Полный make check дополнительно выполняет существующие native E5 проверки на заранее доступных публичных весах, settings/menu synthetic рендеры и миграционные гонки. Build-only изолированный search host проверяет явный список core-зависимостей; не запускает приложение. Реальные OpenRouter, пользовательские материалы, Keychain, звонок, recording/capture/ASR, новые загрузки модели, Constance и календарь не использовались. Качество семантического извлечения на реальных проектах этим не заявляется. Независимое ревью точного PR SHA остаётся следующим обязательным шагом.
