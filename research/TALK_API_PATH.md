# API Толка: границы подключения и записи

Проверено 30 октября 2026 по официальной спецификации:

- [PAT](https://developer.kontur.ru/doc/talk.personal-access-token.api).
- [Public API](https://developer.kontur.ru/doc/talk.public.api).
- [JSON PAT](https://developer.kontur.ru/api/documentations/talk.personal-access-token.api/view), поле specification. Ответ получен без авторизации; совпадает со ссылкой «Скачать JSON» на странице.

## Что подтверждает PAT

Запрос GET /api/Users/profile проверяет, принят ли персональный ключ указанным пространством. В профиле есть имя и название пространства; нет ключа пользователя, активной комнаты или статуса участия. Успех этого запроса не подтверждает доступ к вебхукам и не включает API-автозапись.

Спецификация PAT не содержит метода определения текущей комнаты. GET /api/Rooms/{roomName}/online-users возвращает участников заранее известной комнаты. Для сопоставления зарегистрированного участника есть userInfo.key; uniqueId описан как идентификатор участника конференции, равенство ключу пользователя не гарантируется. Состояние относится к аккаунту, а не конкретному Mac. По окончательному решению пользователя режим опирается на звонки только с этого Mac, без mic gate/кнопки на каждый звонок; native readiness проверяется отдельно.

По умолчанию лимит PAT — 50 запросов в минуту на пользователя, общий для его токенов. Ошибки доступа и сети нельзя интерпретировать как отсутствие встречи.

## Альтернатива с вебхуками

Public API описывает UserConnectedToRoom и UserDisconnectedFromRoom, включая переподключения. Для вебхуков нужны права application.webhooks.read/write и принимающий внешние POST сервер. Документация требует ответ 200 за 5 секунд, активацию и проверку секрета. PAT не заменяет ключ пространства. Сервер и его конфигурация не согласованы; приёмник не создавался.

## Решение пользователя

30 октября пользователь выбрал: «Пока сделать подключение и запись; выбор режима позже».

Первая часть этапа: защищённое поле PAT, сохранение в Keychain вместе с адресом, удаление и явная проверка доступа к профилю. Сохранённый ключ не переносится на другой адрес. Ответы сервера и произвольные тексты сетевых ошибок не выводятся.

Следующая независимая часть: надёжность захвата и индикации существующей записи. До выбора способа определения комнаты действует прежняя эвристика, обозначенная в интерфейсе. API-режим не подменяется этой эвристикой.

Живой PAT ещё не введён. Права и сценарии входа/выхода, mute, переподключения, сна Mac и телефона не проверены. Для живой проверки пользователь вводит PAT только в защищённое поле приложения; действия согласуются отдельно. Календарь и серверная запись не подключаются.

## Уточнение 31 октября 2026: PAT и список комнат

Пользователь выбрал «Да, персональный ключ и список комнат». Это отменяет прежнее откладывание режима. Первая часть #38 — отдельный observer, без включения записи. UI списка/идентичности и production-интеграция остаются следующими частями #3.

Публичный JSON PAT повторно прочитан 31 октября обычным HTTPS GET без credentials (web-инструмент оба URL открыть не смог; curl получил JSON). SHA-256 полученного документа: `a1cad7930490fdd9d658052766e0ce600b9c62be64fa08a62dc1e9fed3167a01`. Это проверка опубликованного контракта, не живого пространства.

В schema по-прежнему нет user key у `/api/Users/profile`. Участник комнаты имеет `userInfo.key`; `uniqueId` обозначает участника конференции. Документированные `/api/Users` (поиск, в том числе по email) и `/api/Users/scan` возвращают пользовательские key, login, email. Они позволяют предложить аккаунт для явного подтверждения пользователем, но сами не доказывают, что выбранный аккаунт выпустил PAT. Нельзя связывать его с PAT по совпадению имени. Вопрос поиска/подтверждения себя задан до UI/runtime реализации; текущий сервис принимает явно переданный user key. `/api/context`, упомянутый во внутренних описаниях полей, не включён в список PAT paths; он не используется.

50 запросов/минуту на пользователя по-прежнему общий лимит всех PAT. `Retry-After` в PAT JSON не описан: клиент поддерживает стандартные delta-seconds и HTTP-date, если заголовок фактически пришёл; без него или при неверном значении ждёт минимум 60 секунд. Наличие этого заголовка у сервера не объявляется подтверждённым. Контракт observer и синтетические проверки — [TALK_ROOM_OBSERVER.md](TALK_ROOM_OBSERVER.md).
